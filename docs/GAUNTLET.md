## Fase 0 — Objetivo, riesgos y autorización

El usuario pidió un servidor multimedia privado estilo Plex, reproducible desde una webapp, alojable en VPS o de forma local, con usuarios autorizados, discos locales, nube y enlaces de torrents. El proveedor elegido es Google Drive. La paridad literal con el catálogo, licencias, clientes propietarios, DRM, TV/DVR y servicios de Plex no se promete.

El usuario pidió que Google se vincule mediante redirección web y que los magnets se reproduzcan sin importarse a la biblioteca. La cuenta Google quedó enlazada en producción con scope `drive.readonly`; el montaje rclone y un vídeo remoto ya se probaron. La transmisión torrent mantiene una caché temporal de piezas verificadas y las elimina al detener/expirar.

Destino aceptado: VPS `devops@192.168.1.250`; dominio `jrplexps.duckdns.org`. El tráfico público termina TLS en nginx de `192.168.1.34` y viaja al TLS interno de `.250`, cuya huella se valida desde el borde. El operador aplicó el vhost y el certificado público; los logs proporcionados se conservan como evidencia atribuida al operador en [`../deploy/PUBLICATION.md`](../deploy/PUBLICATION.md). No se cambió nginx en esta sesión.

Los riesgos principales son filtración de sesiones o tokens; acceso cruzado entre bibliotecas; alcance amplio de OAuth de Drive; montaje ausente que parezca biblioteca vacía; caída/cuota del proveedor; abuso o falta de espacio por torrents; recursos de transcodificación y diferencias entre Linux, Windows y macOS. Controles: cookies opacas HttpOnly/Secure/SameSite, CSRF y verificación de origen, tokens Jellyfin solo en servidor, permisos de biblioteca comprobados en cada solicitud, rclone cifrado, scope Drive de solo lectura, montaje read-only, qBittorrent privado y evidencia separada de cada runtime.

## Fases 2–5 — Implementación, pruebas, auditoría y correcciones

Implementación bajo `JRPlex/`: gateway Node, frontend, Compose, Jellyfin, qBittorrent opcional, enlace OAuth Web de Google, montador rclone read-only, almacenamiento y guías operativas. La iteración de Google Drive se publicó en `.250`; el estado en vivo y sus límites están en la evidencia dedicada.

La corrección de `.d.ts` ya no conserva tarjetas de diagnóstico en el catálogo: `.ts`, `.d.ts`, `.d.mts` y `.d.cts` se excluyen de vídeo y torrent, aunque existan pistas obsoletas. Las fichas de medios reproducibles siguen mostrando nombre, ruta, tipo, contenedor, tamaño y pistas al administrador, y ocultan rutas a cuentas ordinarias. MP4, MKV, AVI y MP3 siguen permitidos según su tipo de biblioteca.

La sección **Carpetas** recorre solo las vistas que Jellyfin expone al usuario actual y busca bajo la carpeta seleccionada. El selector administrativo permite recorrer `/media/local` y `/media/cloud` mediante el API protegido de Jellyfin, sin añadir un montaje FUSE al gateway. La instancia no tiene archivos MP3 indexados ni biblioteca Music; el administrador debe elegir la carpeta de música y escanearla.

El flujo torrent conserva piezas verificadas y almacenamiento temporal en incompletos. Antes de enviar el primer 200 espera la pieza inicial; MKV, AVI y otros contenedores no compatibles se alimentan por tubería a FFmpeg y salen como MP4 fragmentado H.264/AAC. La página indica espera y errores de reproducción en lugar de ocultarlos. Un MKV sintético fue reproducido por la función de streaming en el gateway real y `ffprobe` confirmó contenedor y códecs. No se probó un swarm real.

Durante esta verificación, el panel marcaba qBittorrent como no disponible. El API real respondió 204 con una cookie `QBT_SID_<puerto>` (formato de qBittorrent 5.2.4), mientras JRPlex esperaba HTTP 200, texto `Ok.` y cookie `SID`. Se actualizó el cliente para aceptar los formatos nuevo y anterior; el panel ahora distingue el estado sin revelar credenciales. La suite completa pasó en VPS (33 aprobadas, 0 fallidas, 1 prueba opcional omitida), y una comprobación directa autenticó el API real sin agregar un magnet. qBittorrent y Jellyfin conservaron ID y cero reinicios; solo se recreó el gateway. La URL pública devolvió HTTP 200 con TLS verificado y `/healthz` respondió `ok`.

El magnet compartido no se usó ni se contactó su swarm. Las pruebas sintéticas cubren el formato, la sesión qBittorrent, rangos, espera de pieza verificada y borrado simulado; no acreditan un swarm real. El flujo Google Drive se desplegó y se verificó con una cuenta real y un vídeo real. El primer intento de la suite completa detectó que una prueba esperaba el texto de error en inglés, aunque el helper devuelve el mensaje equivalente en español; se amplió la aserción bilingüe y la suite VPS terminó con 42 aprobadas, 0 fallidas y 1 omitida. ### Diseño OAuth Web y validación en producción

La pantalla redirige a Google y regresa por `response_mode=form_post`; el servidor valida state aleatorio de un solo uso. Guarda el token con AES-256-GCM fuera del código; el cliente y la clave se montan como archivos read-only. El montador entrega a rclone un remoto `drive.readonly` solo en el entorno del proceso, con `--read-only` y caché limitada. Hay ejemplos de unidades systemd que esperan a que FUSE monte antes de iniciar Compose. La clave AES queda en un archivo privado independiente; un gestor externo de secretos del SO no está integrado todavía.
